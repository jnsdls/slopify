# Media keys and Now Playing for a menu-bar Electron app

Resolves issue #6. Question: how do keyboard media keys, AirPods buttons, and the macOS Now Playing widget reach a background Electron app, and what changes if the app is only a Spotify Connect remote with no audio of its own.

## Short answer

Everything on macOS funnels through one pair of system objects: `MPNowPlayingInfoCenter` (what the widget shows) and `MPRemoteCommandCenter` (play, pause, next, previous from keyboard, AirPods, Control Center). Chromium already wraps both, and exposes them to the renderer as `navigator.mediaSession`. That path only works while a media element is actually playing audio in the renderer. If the app produces no audio, MediaSession is inert, `globalShortcut` is the fragile fallback, and the honest fix is a small native addon that talks to the two Apple objects directly.

## How macOS routes media commands

Apple's `MPRemoteCommandCenter` is "an object that responds to remote control events sent by external accessories and system controls", available on macOS since 10.12.2 ([Apple](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter)). `MPNowPlayingInfoCenter` is the companion "object for setting the Now Playing information for media that your app plays", same macOS floor ([Apple](https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter)).

The macOS-specific trap is `playbackState`. Apple's doc says "This property only applies to macOS. You must set this property every time the app begins or halts playback, otherwise remote control functionality may not work as expected" ([Apple](https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter/playbackstate)). A Catalyst developer on the Apple forums hit exactly this: media keys launched Music and nothing showed in Control Center until they set `playbackState = .playing`, after which the app appeared in Now Playing and received commands ([Apple forums](https://developer.apple.com/forums/thread/685333)). The system owns the routing. Whichever app last declared itself playing gets the keys; if nobody has, macOS launches Music.

AirPods buttons are not keyboard events. Electron closed the request to register headphone play/pause through `globalShortcut` as wontfix ([electron#7459](https://github.com/electron/electron/issues/7459)). Only the remote command center path receives them.

## Path a: audio plays in the renderer (Web Playback SDK)

This is the good case. Chromium's macOS system media controls set title, artist, album, artwork, duration, elapsed time, and playback rate on `MPNowPlayingInfoCenter`, and map its internal playing, paused, and stopped states onto `MPNowPlayingPlaybackState` ([now_playing_info_center_delegate.mm](https://chromium.googlesource.com/chromium/src/+/main/components/system_media_controls/mac/now_playing_info_center_delegate.mm)). The matching delegate registers next, previous, play/pause, stop, and seek-to on `MPRemoteCommandCenter` and enables each one only when the page has a handler for it ([remote_command_center_delegate.mm](https://chromium.googlesource.com/chromium/src/+/main/components/system_media_controls/mac/remote_command_center_delegate.mm)). The manager prefers these system controls over the CGEventTap listener and routes incoming keys to the active media session ([media_keys_listener_manager_impl.cc](https://chromium.googlesource.com/chromium/src/+/main/content/browser/media/media_keys_listener_manager_impl.cc)). All of this sits behind the `HardwareMediaKeyHandling` feature, enabled by default on macOS ([media_switches.cc](https://chromium.googlesource.com/chromium/src/+/main/media/base/media_switches.cc)).

So in the renderer: set `navigator.mediaSession.metadata` and register `play`, `pause`, `nexttrack`, `previoustrack` action handlers ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API)). Chrome's own guide adds the constraints that matter here: "Chrome requests 'full' audio focus to show media notifications only when the media duration is at least 5 seconds", "The `title` attribute of the media HTML element is used in the 'Now playing' macOS widget", and you can force the state with `navigator.mediaSession.playbackState` when the browser thinks you are seeking or loading ([web.dev](https://web.dev/articles/media-session)).

It does need audio actually playing. Electron's own patch comment states the rule: Chromium's system media controls fall "down into MPRemoteCommandCenter, which makes it such that an app will not receive remote control events until it begins playing audio" ([electron patch](https://github.com/electron/electron/blob/main/patches/chromium/fix_media_key_usage_with_globalshortcuts.patch)). Metadata set on an idle page shows nothing.

One caveat for the Widevine fork: `navigator.mediaSession.metadata` broke in Electron 15 and was fixed in [electron#31492](https://github.com/electron/electron/pull/31492) ([electron#31448](https://github.com/electron/electron/issues/31448)). Worth a smoke test on whichever castLabs release we pin, since that fork lags upstream.

## Path b: remote only, no audio

MediaSession gives us nothing here. Two options remain.

`globalShortcut` with `MediaPlayPause`, `MediaNextTrack`, `MediaPreviousTrack`. Electron documents that on macOS 10.14 and later these "will not register successfully" unless the app is a trusted accessibility client, checked with `systemPreferences.isTrustedAccessibilityClient(prompt)`, and that a taken accelerator fails silently ([global-shortcut](https://www.electronjs.org/docs/latest/api/global-shortcut), [system-preferences](https://www.electronjs.org/docs/latest/api/system-preferences)). Under the hood Electron patches Chromium to keep a CGEventTap `MediaKeysListener` alive on macOS precisely because the remote command center path needs audio ([electron patch](https://github.com/electron/electron/blob/main/patches/chromium/fix_media_key_usage_with_globalshortcuts.patch)). That patch has broken repeatedly across Chromium roll-ups: Electron 6 ([#20788](https://github.com/electron/electron/issues/20788)), 8 ([#24052](https://github.com/electron/electron/issues/24052), [#22405](https://github.com/electron/electron/issues/22405)), and 13 through 15 ([#30543](https://github.com/electron/electron/issues/30543), fixed in [#30552](https://github.com/electron/electron/pull/30552)). Every time, the symptom was the play key launching Music. It also steals the keys from Music and Spotify desktop for as long as we hold them, requires an Accessibility prompt, and never sees AirPods. I would not ship this as the primary mechanism.

A native addon. Call `MPNowPlayingInfoCenter.default().nowPlayingInfo` and `playbackState`, and add targets to `MPRemoteCommandCenter.shared()` commands, from a small Objective-C or Swift Node addon in the main process. This is the same thing Chromium does internally, minus the requirement that Chromium's own audio pipeline is running. It gets keyboard, AirPods, and the widget in one shot, with no Accessibility permission, and the remote can publish the Connect device's track metadata. The cost is a native build step and keeping `playbackState` in sync with the Connect player state, which Apple says is mandatory on macOS.

A silent looping audio element to keep MediaSession alive is possible but I would treat it as a hack. Chrome only grants full audio focus for media of at least 5 seconds ([web.dev](https://web.dev/articles/media-session)), so it can be made to work, but it burns an audio session and confuses the system's idea of who is playing.

## Recommendation

Path a: MediaSession in the renderer, nothing else. Path b: native addon against `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter`. If both paths must coexist, the addon is the single owner of Now Playing state and MediaSession is disabled with `app.commandLine.appendSwitch('disable-features', 'HardwareMediaKeyHandling')` so the two do not fight over the command center ([media_switches.cc](https://chromium.googlesource.com/chromium/src/+/main/media/base/media_switches.cc), [electron#21731](https://github.com/electron/electron/issues/21731)).
