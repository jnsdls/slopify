# slopify v1

A macOS menu-bar app that signs in one Premium Spotify account and plays a Playlist or Liked Songs, with play/pause, next and volume. Audio comes out of the app itself. Vocabulary is in [`CONTEXT.md`](../../CONTEXT.md); capitalised terms below (Listener, Source, Player, Dropdown, Picker, Resume Point, Sign-in State) are defined there.

This document is the hand-off. It comes out of [the wayfinder map](https://github.com/jnsdls/slopify/issues/2) and the tickets under it. Every non-obvious fact here was verified by a spike or a research ticket on this repo; the tickets are linked where the detail matters. Branches named `spike/*` hold working throwaway code and are the reference for anything this spec leaves ambiguous.

## Scope

In: sign in, pick a Source from own and followed playlists, a pasted playlist link, or Liked Songs; play, pause, next, volume; resume the last Source at launch; media keys, AirPods and the macOS Now Playing widget; a packaged `slopify.app` the owner builds locally.

Out, and not to be sneaked in: Radio, public login, albums as a Source, search as browsing, queue editing, seek, shuffle or repeat toggles, sign out, previous-track button, lyrics, crossfade, auto-update, notarisation, Windows, Linux. Remote mode (driving another Spotify Connect device) is ruled out by [ADR 0001](../adr/0001-in-app-playback-via-castlabs-electron.md).

The audience is the owner plus at most four allowlisted Listeners, all on Premium. Spotify Development Mode caps a client at five users, and the app's client id was registered after February 2026, so the reduced endpoint set applies. Everything the app calls is on the retained list ([research](https://github.com/jnsdls/slopify/issues/13)).

## Stack

- castLabs Electron pinned at `v44.1.0+wvcus` (Electron 44.1.0, Chrome 152, Widevine CDM fetched on first launch). Installed as `pnpm add -D "https://github.com/castlabs/electron-releases#v44.1.0+wvcus"` with `pnpm.onlyBuiltDependencies: ["electron"]`. Do not bump it; the licence check was run against this exact build ([spike](https://github.com/jnsdls/slopify/issues/3)).
- TypeScript, electron-vite, pnpm. No UI framework; the renderer is hand-written HTML, CSS and TypeScript.
- Vitest for unit tests. ESLint and `tsc --noEmit` in `pnpm check`.
- electron-builder for packaging, plus the `castlabs-evs` Python package for VMP signing.
- package.json `name` is `slopify` and `productName` is `slopify`. `app.getPath('userData')` follows `name`, so this fixes `~/Library/Application Support/slopify`.

Layout follows electron-vite's default: `src/main`, `src/preload`, `src/renderer`. The main process owns tokens, the Web API, persisted state, the tray and the window. The renderer owns the Player and the Dropdown. Nothing in the renderer holds a refresh token or calls the Web API directly.

## Processes and the bridge

`contextIsolation` on, `nodeIntegration` off, `sandbox` on. The renderer is loaded from the packaged `index.html` on `file://`. Its content security policy must allow `https://sdk.scdn.co` for the SDK script, `https://*.spotify.com` and `https://*.scdn.co` for the SDK's own traffic, and `https://i.scdn.co` for artwork.

Set `webPreferences.autoplayPolicy` to `no-user-gesture-required`. The app starts playback from the main process at launch, with no click, and the spikes relied on this being Electron's default. Pin it so a future default change does not surface as `autoplay_failed`.

The preload exposes one object, `window.slopify`, with this shape. The renderer never sees anything else.

```ts
type Source =
  | { kind: 'playlist'; id: string; uri: string; name: string; imageUrl: string | null; pasted: boolean }
  | { kind: 'liked' };

type ResumePoint = { source: Source; trackUri: string | null; positionMs: number };

type AuthState =
  | { kind: 'signed-out'; reason: 'first-run' | 'expired' | 'not-premium' | 'error'; detail?: string }
  | { kind: 'signing-in' }
  | { kind: 'signed-in'; displayName: string; userId: string };

interface SlopifyBridge {
  // auth
  getAuthState(): Promise<AuthState>;
  onAuthState(cb: (s: AuthState) => void): () => void;
  signIn(): Promise<void>;                 // opens the browser, resolves when the callback lands
  getAccessToken(): Promise<string>;       // fresh token for the SDK's getOAuthToken

  // sources
  listSources(): Promise<Source[]>;        // Liked Songs first, then playlists in Spotify's order
  resolvePastedLink(text: string): Promise<Source>;   // throws { code: 'bad-link' | 'not-found' | 'forbidden' }

  // playback commands that go through the Web API (the SDK handles the rest)
  startSource(source: Source, resume?: { trackUri: string | null; positionMs: number }): Promise<void>;
  transferHere(): Promise<void>;
  getPlayingElsewhere(): Promise<{ deviceName: string } | null>;

  // state the main process persists
  getResumePoint(): Promise<ResumePoint | null>;
  saveResumePoint(p: ResumePoint): void;
  getVolume(): Promise<number>;
  saveVolume(v: number): void;

  // player identity
  reportDevice(deviceId: string | null): void;   // renderer tells main the SDK device id, or null on not_ready

  // shell
  openExternal(url: string): void;
  quit(): void;
  hideWindow(): void;
}
```

`startSource` and `transferHere` need the SDK device id; the main process keeps the last value from `reportDevice` and rejects with `{ code: 'no-device' }` if it is null.

## Auth

Authorization Code with PKCE. No client secret exists and none is needed.

- Client id `a768335a56b648d4a6d11d945d029ce4`, public, hard-coded.
- Redirect URI `http://127.0.0.1:8888/callback`, fixed. The dashboard refused a portless loopback, so the port cannot be dynamic ([ticket](https://github.com/jnsdls/slopify/issues/4)).
- Scopes: `streaming user-read-email user-read-private user-read-playback-state user-modify-playback-state playlist-read-private playlist-read-collaborative`. The first three are what the SDK documents as required. `user-library-read` is not needed; playing Liked Songs as a context worked without it ([spike](https://github.com/jnsdls/slopify/issues/14)).

Sign-in flow, triggered by the button in the Sign-in State:

1. Generate `code_verifier` (64 random bytes, base64url), `code_challenge` (S256) and a random `state`.
2. Start an HTTP server bound to `127.0.0.1:8888`. If the port is taken, reject and show "Port 8888 is in use" in the Sign-in State. The server accepts one request and then closes; it also closes after five minutes.
3. Open `https://accounts.spotify.com/authorize` in the default browser with `response_type=code`, the client id, redirect URI, scopes, `code_challenge_method=S256`, the challenge and the state.
4. On `/callback`, check the state, exchange the code at `https://accounts.spotify.com/api/token` (`grant_type=authorization_code`, `client_id`, `code_verifier`, `redirect_uri`). Respond to the browser with a one-line HTML page saying the tab can be closed.
5. Store the refresh token (below), keep the access token and its expiry in memory, call `GET /me` for `id` and `display_name`, and publish `signed-in`.

The refresh token is a generic password in the login Keychain, service `slopify-spotify-refresh-token`, account the Spotify user id. Read and write by spawning `/usr/bin/security`; no native addon. Write with `-T /usr/bin/security` and never `-A`. The value goes in on stdin, not as an argument. Reason for the CLI over Electron's `safeStorage` or `keytar`: the app is ad-hoc signed, so its code identity changes on every build, and Keychain items whose ACL trusts the app would prompt after each rebuild. Items that trust `/usr/bin/security` do not.

```sh
# read
security find-generic-password -s slopify-spotify-refresh-token -w
# write (value piped on stdin)
security add-generic-password -a "$USER_ID" -s slopify-spotify-refresh-token -U -T /usr/bin/security -w
# delete (only on invalid_grant)
security delete-generic-password -s slopify-spotify-refresh-token
```

Access tokens last an hour. Refresh five minutes before expiry, and on any 401 from the Web API. The refresh call is `POST https://accounts.spotify.com/api/token` with `grant_type=refresh_token`, `refresh_token`, `client_id`. Spotify may rotate the refresh token in the response; store the new one when present. `getAccessToken` from the renderer returns the cached token if it has more than five minutes left, otherwise refreshes first.

Refresh failures, decided on the [spec ticket](https://github.com/jnsdls/slopify/issues/10):

- Network error or 5xx: retry with backoff (2 s, 4 s, 8 s, then every 30 s). Playback keeps going on the current access token until it expires. Nothing shown to the Listener unless the token actually expires, at which point the Dropdown shows "Reconnecting to Spotify" in the progress area.
- `400 invalid_grant` (the refresh token is dead; Spotify expires them after six months of PKCE use, or the Listener revoked access): delete the Keychain item, publish `signed-out` with reason `expired`, switch the tray icon to the attention variant. Playback continues until the access token expires, then the Player disconnects. Signing in again restores the Resume Point, paused.

There is no sign-out. To switch accounts, delete the Keychain item.

Premium is not checked up front. Development Mode removed `product` from `GET /me`, so the only signal is the SDK's `account_error` event, which fires for non-Premium accounts. On that event the main process publishes `signed-out` with reason `not-premium` and leaves the refresh token in place.

## The Player

The renderer loads `https://sdk.scdn.co/spotify-player.js` and creates one `Spotify.Player` named `slopify`, `getOAuthToken` wired to `slopify.getAccessToken`, initial volume from `slopify.getVolume`. Connect on startup, as soon as the auth state is `signed-in`.

Events, and what each does:

- `ready`: call `slopify.reportDevice(device_id)`. On the first `ready` after launch, run the launch sequence below.
- `not_ready`: `reportDevice(null)`. Show "Reconnecting" in the progress area. If no `ready` follows within 30 s, call `player.connect()` again, and keep doing so every 30 s. Sleep and wake, and network loss, both land here.
- `player_state_changed` with a state: update the Dropdown, update `navigator.mediaSession`, and call `saveResumePoint` (throttled to once every 5 s while playing, immediately on pause and on track change).
- `player_state_changed` with `null`: another device took over. Show "Playing on <name>" (see Dropdown states) and poll `getPlayingElsewhere` every 10 s while in that state.
- `initialization_error`, `authentication_error`: log, then `getAccessToken` and `connect()` again once. A second failure shows the `error` reason in the Sign-in State.
- `account_error`: report to main as not-premium (above).
- `playback_error`: show the message in the progress area for 5 s. If it repeats three times within a minute, stop retrying and leave the message up. This is the state the DRM path fails into; the spike saw a 500 from the licence server surface here.

Progress display interpolates locally: keep `position` and the timestamp of the last state event and tick every 500 ms while `paused` is false. Never call `getCurrentState()` on a timer.

Transport goes straight through the SDK: `togglePlay()`, `nextTrack()`, `setVolume(v)` where `v` is 0 to 1. `previousTrack()` is wired to the media key only; the Dropdown has no button. Volume changes call `saveVolume` debounced at 300 ms.

Shuffle and repeat are set once per `startSource`, after the play call: `PUT /me/player/shuffle?state=false&device_id=` and `PUT /me/player/repeat?state=context&device_id=`. Shuffle off first, then repeat. Treat any 2xx as success; this account gets 200 with a body where the docs say 204. Setting shuffle before the first play matters: the spike saw the start order drift until it was set.

### Launch sequence

On the first `ready` after launch, if a Resume Point exists:

1. `player.setVolume(0)`.
2. `slopify.startSource(source, { trackUri, positionMs })`.
3. On the first `player_state_changed` that names the resumed track, `player.pause()`, then restore the saved volume.
4. If the play call fails with a 404 or 403 (a Playlist that has gone away, or a Pasted Playlist the account can no longer see), clear the Resume Point and show the empty state.

Muting first means the resume produces no audible blip. If no Resume Point exists, the Dropdown shows the empty state until a Source is picked.

### Now Playing and media keys

`navigator.mediaSession` is the whole mechanism. No `globalShortcut`, no native addon, no Chromium flags ([research](https://github.com/jnsdls/slopify/issues/6), [smoke test](https://github.com/jnsdls/slopify/issues/11)). On every state event:

- `mediaSession.metadata = new MediaMetadata({ title, artist, album, artwork: [{ src: <largest image>, sizes, type: 'image/jpeg' }] })`.
- `mediaSession.playbackState` = `'playing'` or `'paused'`.
- `mediaSession.setPositionState({ duration, position, playbackRate: 1 })`.

Register handlers for `play`, `pause`, `nexttrack`, `previoustrack` and `stop` (stop pauses). `previoustrack` is registered even without a button so the key does not fall through to Music.

macOS lets whichever app last set `playing` own the keys. If Spotify desktop is open it mirrors the Connect session and takes Now Playing; the keys still reach playback through Spotify, only the ownership moves. v1 assumes Spotify desktop is closed and says so in the README. One physical F8 press by the owner is the acceptance test; synthetic key events cannot verify this.

## Sources

`listSources` returns Liked Songs first, then `GET /me/playlists?limit=50`, following `next` until null, mapped to `Source` with `pasted: false`. Followed playlists are included by that endpoint. Cache the list for the life of the process and refresh when the Picker opens, but render the cached list first.

`resolvePastedLink` accepts `https://open.spotify.com/playlist/<id>` with any query string, `spotify:playlist:<id>`, and a bare 22-character base-62 id. Anything else rejects with `bad-link`. It then calls `GET /playlists/<id>?fields=name,uri,images,owner.id`. A 404 rejects with `not-found` (covers Spotify-owned editorial and algorithmic playlists, which Development Mode apps lost in November 2024). A 403 rejects with `forbidden`. Track counts are not available for playlists the Listener does not own, so the Picker never shows one.

A Pasted Playlist is the Source only while current. It is not remembered in the Picker after another Source is picked. If the Listener wants it to stick, they follow it in Spotify and it turns up under playlists.

`startSource` is one call per Source kind, always with `?device_id=<sdk>`:

| Source | `PUT /me/player/play` body |
| --- | --- |
| Playlist | `{ "context_uri": "spotify:playlist:<id>" }` |
| Liked Songs | `{ "context_uri": "spotify:user:<userId>:collection" }` |

With a resume argument, add `"offset": { "uri": "<trackUri>" }` and `"position_ms": <n>`. Offsets by uri were verified on both kinds ([spike](https://github.com/jnsdls/slopify/issues/14)). If the play call returns 4xx with an offset, retry once without it: the track may have left the Playlist.

The collection URI is undocumented. The spike on 2026-09-09 shows it works with offsets, against the 2021 reports that offsets were refused. If Spotify removes it, the fallback is paging `GET /me/tracks` (needs `user-library-read`) into a `uris` list of at most 100 and topping up through `POST /me/player/queue`. That path is not built in v1; the [playback research](https://github.com/jnsdls/slopify/issues/13) has the details.

`transferHere` is `PUT /me/player` with `{ "device_ids": ["<sdk>"], "play": true }`.

## Resume Point and persisted state

One JSON file, `<userData>/state.json`, written atomically (write to a temp file, rename):

```json
{
  "version": 1,
  "resume": { "source": { "kind": "playlist", "id": "…", "uri": "…", "name": "…", "imageUrl": "…", "pasted": false }, "trackUri": "spotify:track:…", "positionMs": 83210 },
  "volume": 0.6
}
```

Unknown `version` means start fresh. Missing file means first run: set launch-at-login (below) and show the Sign-in State.

## The Dropdown

Variant A from the [prototype](https://github.com/jnsdls/slopify/issues/9), rebuilt properly. Reference: `prototype/dropdown/index.html?variant=A` on the `prototype/dropdown` branch, screenshot at `prototype/dropdown/shots/A.png` there. The code is throwaway; the layout is the decision.

300 px wide. Height fits content, at most 560 px. Top to bottom:

1. Artwork, square, full width, corners at 4 px, from the largest image on the track's album.
2. Title, one line, ellipsised, and itself a link to the track on `open.spotify.com` through `openExternal`. Artist line under it, all artists joined with commas, the first artist linked the same way.
3. Progress bar with elapsed on the left and total on the right, `m:ss`. Display only, no seek.
4. Transport centred: one round play/pause button and a next button. No previous.
5. Volume slider, 0 to 100, no mute button.
6. "Playing from" row: the Source's thumbnail (Liked Songs uses a fixed heart tile) and name. Clicking opens the Picker in place.
7. Footer: full Spotify logo on the left (see Attribution), the Listener's display name, Quit on the right.

The Picker replaces items 1 to 5 with a list while open, keeping the footer. Order: Liked Songs, then playlists as `listSources` returns them, each with its thumbnail and name and a check on the current one, then a text field "Paste a playlist link" at the end. Picking a row calls `startSource` without resume and collapses the Picker. Pasting a link and pressing Enter resolves it, plays it on success, or shows the error inline under the field: "That's not a playlist link", "Spotify won't share that playlist with this app" for `not-found` and `forbidden`. Escape closes the Picker before it closes the window.

### States

- Playing or paused: the layout above. Play/pause reflects `paused`.
- Empty (signed in, no Source yet): artwork slot shows the app icon dimmed, title reads "Pick something to play", transport disabled, "Playing from" row reads "Choose a source" and opens the Picker.
- Playing elsewhere: artwork and title from `GET /me/player` if it returns an item, progress area reads "Playing on <device>". The play button is enabled and calls `transferHere`; next and volume are disabled.
- Reconnecting: progress area reads "Reconnecting", transport disabled.
- Sign-in State: replaces everything but the footer. One line of text and a "Sign in with Spotify" button. The line depends on the reason. First run: "Sign in to start playing." Expired: "Spotify signed you out. Sign in again to keep going." Not premium: "slopify needs a Premium account." Error: the detail. While `signing-in`, the button is disabled and reads "Waiting for Spotify".

Keyboard while the window is focused: Space toggles play/pause, Right arrow is next, Escape closes the Picker or the window. Nothing global.

## Menu bar and window

- `Tray` with a monochrome template image, 22 pt with a 2x asset. One variant for normal, one with a small dot for attention (used only for the `expired` Sign-in State). No title text.
- No Dock icon: `LSUIElement` true through electron-builder's `mac.extendInfo`, and `app.dock.hide()` at startup for the unpackaged dev run.
- The Dropdown is a frameless, non-resizable `BrowserWindow`, `show: false` until first use, `alwaysOnTop`, `skipTaskbar`, `hiddenInMissionControl`, positioned under the tray icon from `tray.getBounds()` and clamped to the screen's work area. Left and right click both toggle it. It hides on blur and on Escape. Hiding does not destroy it; the Player lives in this window, so the window must never be closed while the app runs.
- Launch at login: `app.setLoginItemSettings({ openAtLogin: true })` on first run only. No toggle in the app; System Settings switches it off.
- `ELECTRON_RUN_AS_NODE` in the environment makes the binary start as Node and exit. The packaged build turns the `runAsNode` fuse off (packaging section). Dev scripts run with `env -u ELECTRON_RUN_AS_NODE`.

## Attribution

Checked against Spotify's design guidelines and developer policy on 2026-09-09 ([research](https://github.com/jnsdls/slopify/issues/15), full checklist with source URLs in `docs/research/spotify-attribution.md` on `research/spotify-attribution`). The Dropdown is a "playing view" in Spotify's terms, so the rules below are required, not nice to have.

- The footer shows the full Spotify logo (icon plus wordmark), at least 70 px wide, with clear space of half the icon height on every side. Use the asset from Spotify's own download, unmodified. Never the wordmark alone.
- The logo is monochrome. Spotify green is allowed only on pure black or pure white, and the Dropdown background is neither. White logo on the dark appearance, black on light. The Dropdown follows the system appearance for this reason alone; everything else may stay dark.
- The title links to the track and the artist line links to the first artist, both on `open.spotify.com`. The link beside the title from the prototype becomes the title itself being the link; no separate icon. Metadata must link to the matching entity, never to Spotify's home page.
- Artwork is shown uncropped, no overlay of any kind (no play glyph, no gradient, no text), no blur, no animation, corners rounded at 4 px. The empty state's dimmed app icon is fine because it is not Spotify content.
- Metadata is rendered exactly as the SDK returns it. Truncated title or artist gets a `title` attribute with the full string.
- No playback happens without artwork and metadata on screen when the Dropdown is open. Closed Dropdown counts as a minimised view, and Now Playing carries the same metadata, so playback with the window hidden is fine. Do not add a mode that hides metadata.
- Artwork and metadata are cached only for display (the renderer's HTTP cache). No audio is ever written to disk by the app; Widevine keeps the decoded stream in the CDM.
- The app icon and tray icon must not resemble the Spotify mark: no green, no circle-with-waves.
- The name "slopify" passes the letter of the naming rule (does not contain "Spotify", does not start with "Spot") but is close enough to revisit before any public release, which is out of scope anyway. The Connect device name is `slopify`.
- Spotify's policy wants a way to disconnect the app. v1 has no sign-out; the disconnect is the Listener revoking access at spotify.com/account/apps, which the app handles through the `invalid_grant` path.
- Policy asks that the app add value beyond Spotify's own client. The README says what that is: a one-click Source from the menu bar with no Spotify desktop running.

## Error handling summary

| Situation | Signal | What the Listener sees |
| --- | --- | --- |
| No refresh token | startup | Sign-in State, first-run line |
| Refresh token dead | `invalid_grant` | Sign-in State, expired line; tray dot |
| Network down during refresh | fetch error / 5xx | nothing until the access token expires, then "Reconnecting" |
| Non-Premium account | SDK `account_error` | Sign-in State, premium line |
| Licence server refuses | SDK `playback_error` | message in the progress area; stops retrying after three in a minute |
| Another device took over | state `null` | "Playing on <device>", play transfers back |
| Playlist gone | 404/403 on play | Resume Point cleared, empty state |
| Pasted link bad or blocked | `resolvePastedLink` rejects | inline line under the paste field |
| Port 8888 busy | listen error | Sign-in State, error line |
| Spotify desktop open | Now Playing moves to Spotify | nothing in-app; README explains |

Every Web API call retries once on 429 after `Retry-After`, and once on 5xx after 1 s. Log every non-2xx with method, path and status to `<userData>/logs/slopify.log` through `electron-log`, rotated at 1 MB.

## Packaging and signing

From the [packaging spike](https://github.com/jnsdls/slopify/issues/12); `package.sh`, `afterPack.js` and the `build` block on the `spike/castlabs-packaging` branch are the working reference.

`pnpm package` runs, in order:

1. Refresh the EVS token: `python3 -m castlabs_evs.account -n refresh -A "$(security find-generic-password -s castlabs-evs-account-name -w)" -P "$(security find-generic-password -s castlabs-evs-password -w)"`. The token expires monthly; skipping this step is the usual reason a build fails.
2. `electron-vite build`.
3. `electron-builder --mac --dir` with `build` set to `electronDist: node_modules/electron/dist` (without it electron-builder downloads stock Electron, which has no Widevine), `mac.target: dir`, `mac.identity: null` (skip electron-builder's codesign), `mac.extendInfo.LSUIElement: true`, `electronFuses` with `runAsNode: false`, `enableNodeCliInspectArguments: false`, `enableNodeOptionsEnvironmentVariable: false`, and `afterPack: ./afterPack.js`, which runs `castlabs_evs.vmp -n sign-pkg <appOutDir>` then `verify-pkg`.
4. `codesign --force --deep --sign - dist/mac-arm64/slopify.app`, then `codesign --verify --deep --strict` and `castlabs_evs.vmp -n verify-pkg dist/mac-arm64`.

VMP before codesign, always. Ad-hoc codesign after VMP was verified to leave the VMP signature valid. The fuse step is the one thing the spike did not run: if `verify-pkg` fails after fuses are flipped, move the fuse flip before `sign-pkg` (electron-builder's `afterPack` runs after fuses, so this would mean running `@electron/fuses` from `package.sh` before electron-builder) and re-verify. Whatever order works goes into `package.sh` with one comment naming this paragraph.

The EVS streaming signature is cached by binary hash and is valid until about 2030; only the account token needs the monthly refresh. Credentials: EVS account `jnsdls`, Keychain services `castlabs-evs-account-name` and `castlabs-evs-password`.

Output is `dist/mac-arm64/slopify.app`. Copy it to `/Applications` by hand. No DMG, no notarisation, no update mechanism.

## Testing and done

Unit tests, Vitest, in the main process code:

- PKCE: verifier and challenge generation match RFC 7636 test vectors; the authorize URL carries every scope; the callback rejects a wrong `state`.
- Token store: refresh five minutes before expiry, rotate the refresh token when the response carries one, `invalid_grant` clears the Keychain item and publishes `expired`, network errors back off and do not sign out.
- Pasted link parser: the three accepted forms with and without query strings, and rejection of track, album and artist links.
- State file: round-trips, atomic write, unknown version starts fresh.
- `startSource` body builder: the two Source kinds, with and without resume, and the retry without offset on 4xx.

Manual checklist, done by the owner on the packaged app before v1 is called finished:

1. Fresh `~/Library/Application Support/slopify`: app shows the Sign-in State, sign in completes in the browser, Dropdown lands in the empty state.
2. Pick Liked Songs: audio within 5 s, licence POST logged as 200.
3. Pick a followed playlist, then a pasted link to a friend's playlist, then a pasted link to a Spotify editorial playlist (expect the inline not-found line).
4. Quit mid-track, relaunch: the same track at the same position, paused, no audible blip.
5. F8, AirPods play/pause and next, and the Now Playing widget shows slopify's title and artwork.
6. Start playback on a phone: Dropdown shows "Playing on <phone>", play in slopify takes it back.
7. Let the playlist run to the end: it loops.
8. Sleep the Mac for a minute, wake: playback resumes on play without a reconnect error.
9. `codesign --verify --deep --strict` and `verify-pkg` pass on the shipped bundle; launching via `open` with `ELECTRON_RUN_AS_NODE=1` in the environment still starts the app.

## Known unknowns

Recorded so the builder does not rediscover them:

- Whether flipping fuses survives VMP signing (packaging section).
