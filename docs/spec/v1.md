# slopify v1

A macOS menu-bar app that signs in one Premium Spotify account and plays a Playlist or Liked Songs, with play/pause, next and volume. Audio comes out of the app itself. Vocabulary is in [`CONTEXT.md`](../../CONTEXT.md); capitalised terms below (Listener, Source, Player, Dropdown, Picker, Resume Point, Sign-in State) are defined there.

This document is the hand-off. It comes out of [the wayfinder map](https://github.com/jnsdls/slopify/issues/2) and the tickets under it. Every non-obvious fact here was verified by a spike or a research ticket on this repo; the tickets are linked where the detail matters. Branches named `spike/*` hold working throwaway code and are the reference for anything this spec leaves ambiguous.

## Scope

In: sign in, pick a Source from own and followed playlists, a pasted playlist link, or Liked Songs; play, pause, next, volume; resume the last Source at launch; media keys, AirPods and the macOS Now Playing widget; a packaged `slopify.app` the owner builds locally.

Out, and not to be sneaked in: Radio, public login, albums as a Source, search as browsing, queue editing, seek, shuffle or repeat toggles, sign out, previous-track button, lyrics, crossfade, auto-update, notarisation, Windows, Linux. Remote mode (driving another Spotify Connect device) is ruled out by [ADR 0001](../adr/0001-in-app-playback-via-castlabs-electron.md).

The audience is whoever builds the app plus at most four Listeners they allowlist on their own Spotify developer app, all on Premium. Spotify Development Mode caps a client at five users, and any client id registered after February 2026 gets the reduced endpoint set, so the app assumes it. Everything the app calls is on the retained list ([research](https://github.com/jnsdls/slopify/issues/13)).

## Stack

- Rust 1.98.1, pinned in `rust-toolchain.toml` with rustfmt and clippy. One Cargo workspace at the repo root, edition 2024.
- GPUI for the Dropdown, taken from `zed-industries/zed` at commit `76659a5` (release `v1.22.0`). Bumping the pin is a deliberate step and gets tested like one ([ADR 0002](../adr/0002-player-in-wkwebview-ui-in-gpui.md)). The `runtime_shaders` feature compiles the Metal shaders at launch, so neither local builds nor CI need the Metal Toolchain.
- `wry` 0.57 for the hidden WKWebView the Player runs in. WebKit gives every WKWebView FairPlay, and the SDK uses it. No castLabs build, no Widevine, no VMP signature ([spike](https://github.com/jnsdls/slopify/issues/22)).
- The `objc2` crates for AppKit, MediaPlayer.framework and ServiceManagement. No Swift, no Objective-C sources.
- `ureq` for every HTTP call: auth, the Web API and artwork. Every call blocks, so the app runs each one on a thread of its own.
- `log` with `env_logger` for logging.

Layout:

- `app/` is the `slopify` binary. `main.rs` wires it up. `app_model.rs` is the one GPUI model the rest hangs off. `player/` is the Player's logic, `player.html` the page it drives, `player_host.rs` the web view that page runs in. `dropdown/` is the GPUI Dropdown and Picker, `status_item.rs` the menu bar icon, `now_playing.rs` Now Playing and the media keys, `login_item.rs` the login item. `image_http.rs` is the HTTP client GPUI fetches artwork with, and `assets.rs` serves the SVG icons from the binary.
- `crates/auth` (`slopify-auth`): PKCE, the loopback callback server, the Keychain and the token store.
- `crates/spotify` (`slopify-spotify`): the Web API client with the retry rules, the Source list and pasted links, the playback commands, and the `Source`, `ResumePoint` and error types.
- `crates/state` (`slopify-state`): the state file.

Rust owns tokens, the Web API, persisted state, the Player's logic, the menu bar icon and both windows. The web view holds one `Spotify.Player` and nothing else. It gets an access token only when the SDK asks for one, never sees the refresh token, and never calls the Web API.

## Architecture and the bridge

GPUI owns the main thread and its run loop. `AppModel` holds the Sign-in State, the Player, the Source list and the SDK device id. The Dropdown observes it, and it notifies on every change, including the 500 ms progress tick.

The Player (`app/src/player/mod.rs`, ported from the Electron renderer's `player.ts`) does no I/O and owns no timers. Every input takes the current time and returns a list of effects: an SDK call, a Web API call, a state file write. `AppModel` carries them out and wakes the Player at its next deadline. Web API and token calls run on a thread each, and their results come back to the Player as inputs. `AppModel` emits `PlaybackChanged` when the track, the paused flag, the duration, the position anchor or the "Playing on" state changes. Now Playing listens for that event. The progress tick does not fire it.

`player_host.rs` builds the web view inside a borderless 480 by 360 `NSWindow` that is never ordered on screen. The page is `app/src/player.html`, compiled into the binary and served from a custom `slopify` protocol at `slopify://player/`. Any other path gets a 404. The custom protocol gives the page a secure context. Autoplay is on through `with_autoplay(true)`, because the app starts playback at launch with no click. The page has no content security policy. It loads `https://sdk.scdn.co/spotify-player.js`, and the SDK brings its own iframe and traffic.

The page posts JSON strings through `window.ipc.postMessage`, tagged by `t`. `app/src/player/page.rs` parses them:

| `t` | Fields | Sent on |
| --- | --- | --- |
| `sdk-loaded` | none | `onSpotifyWebPlaybackSDKReady` |
| `ready` | `deviceId` | SDK `ready` |
| `not-ready` | none | SDK `not_ready` |
| `state` | `state`: `null`, or `{ paused, position, duration, context: { uri }, track_window: { current_track } }` | SDK `player_state_changed` |
| `error` | `event`, `message` | `initialization_error`, `authentication_error`, `account_error`, `playback_error`, and `autoplay_failed` with an empty message |
| `token` | `id` | the SDK's `getOAuthToken` asking for a token |
| `log` | `msg` | a failed SDK call, a page error or an unhandled rejection |

Rust answers by running JavaScript in the page with `evaluate_script`, always a call on `window.slopify`:

- `start(volume)` creates the one `Spotify.Player`, adds the listeners and connects. `AppModel` calls it once, when `sdk-loaded` has arrived and the Listener is signed in.
- `token(id, token)` answers a `token` message. A `null` token drops the callback and leaves the SDK to report its own error.
- `connect()`, `togglePlay()`, `resume()`, `pause()`, `nextTrack()`, `previousTrack()`, and `setVolume(v)` with `v` clamped to 0 to 1. A rejected SDK promise comes back as a `log` message.

`player_host::eval` never logs the script it runs, because a `token` call carries an access token.

The shared types, abridged. The serde attributes keep the JSON identical to the Electron app's TypeScript types, because the state file stores them.

```rust
// crates/spotify/src/types.rs. JSON fields are camelCase.
enum Source {
    Playlist { id: String, uri: String, name: String, image_url: Option<String>, pasted: bool }, // {"kind":"playlist",...}
    Liked,                                                                                         // {"kind":"liked"}
}
struct ResumePoint { source: Source, track_uri: Option<String>, position_ms: u64 }

// Errors the UI switches on. Codes: bad-link, not-found, forbidden, no-device, play-failed.
struct BridgeError { code: BridgeErrorCode, status: Option<u16>, message: Option<String> }

// crates/auth/src/token_store.rs
enum AuthState {
    SignedOut { reason: SignedOutReason, detail: Option<String> }, // FirstRun, Expired, NotPremium, Error
    SigningIn,
    SignedIn { display_name: String, user_id: String },
}
```

`start_source` and `transfer_here` need the SDK device id. `AppModel` keeps the id from the last `ready`, forgets it on `not-ready`, and fails the call with `no-device` while it has none.

## Auth

Authorization Code with PKCE. No client secret exists and none is needed.

- Client id compiled in from `SLOPIFY_SPOTIFY_CLIENT_ID` with `option_env!`. `package.sh` takes it from the environment or `.env.local` and refuses to build without it. A binary built without it logs an error and exits at launch. Public, one per person building the app.
- Redirect URI `http://127.0.0.1:8888/callback`, fixed. The dashboard refused a portless loopback, so the port cannot be dynamic ([ticket](https://github.com/jnsdls/slopify/issues/4)).
- Scopes: `streaming user-read-email user-read-private user-read-playback-state user-modify-playback-state playlist-read-private playlist-read-collaborative`. The first three are what the SDK documents as required. `user-library-read` is not needed; playing Liked Songs as a context worked without it ([spike](https://github.com/jnsdls/slopify/issues/14)).

Sign-in flow, triggered by the button in the Sign-in State:

1. Generate `code_verifier` (64 random bytes, base64url), `code_challenge` (S256) and a random `state`.
2. Start an HTTP server bound to `127.0.0.1:8888`. If the port is taken, reject and show "Port 8888 is in use" in the Sign-in State. The server accepts one request and then closes; it also closes after five minutes.
3. Open `https://accounts.spotify.com/authorize` in the default browser with `response_type=code`, the client id, redirect URI, scopes, `code_challenge_method=S256`, the challenge and the state.
4. On `/callback`, check the state, exchange the code at `https://accounts.spotify.com/api/token` (`grant_type=authorization_code`, `client_id`, `code_verifier`, `redirect_uri`). Respond to the browser with a one-line HTML page saying the tab can be closed.
5. Store the refresh token (below), keep the access token and its expiry in memory, call `GET /me` for `id` and `display_name`, and publish `signed-in`.

The refresh token is a generic password in the login Keychain, service `slopify-spotify-refresh-token`, account the Spotify user id. `crates/auth/src/keychain.rs` reads and writes it by spawning `/usr/bin/security`. No Keychain API is linked into the app. Write with `-T /usr/bin/security` and never `-A`. The token never goes in argv. `-w` with no value reads from the terminal and never from a pipe, so the app writes through `security -i`, which takes whole commands on stdin, with each value single-quoted. The CLI is there because the app is ad-hoc signed, so its code identity changes on every build, and Keychain items whose ACL trusts the app would prompt after each rebuild. Items that trust `/usr/bin/security` do not.

```sh
# read
security find-generic-password -s slopify-spotify-refresh-token -w
# write: `security -i`, with this line on stdin
add-generic-password -a '<user id>' -s slopify-spotify-refresh-token -U -T /usr/bin/security -w '<token>'
# delete (only on invalid_grant)
security delete-generic-password -s slopify-spotify-refresh-token
```

Access tokens last an hour. Refresh five minutes before expiry, and on any 401 from the Web API. The refresh call is `POST https://accounts.spotify.com/api/token` with `grant_type=refresh_token`, `refresh_token`, `client_id`. Spotify may rotate the refresh token in the response; store the new one when present. `TokenStore::access_token`, which answers the page's `token` messages and the Web API client, returns the cached token if it has more than five minutes left, otherwise refreshes first. Concurrent callers share one refresh.

Refresh failures, decided on the [spec ticket](https://github.com/jnsdls/slopify/issues/10):

- Network error or 5xx: retry with backoff (2 s, 4 s, 8 s, then every 30 s). Playback keeps going on the current access token until it expires. Nothing shown to the Listener unless the token actually expires, at which point the Dropdown shows "Reconnecting to Spotify" in the progress area.
- `400 invalid_grant` (the refresh token is dead; Spotify expires them after six months of PKCE use, or the Listener revoked access): delete the Keychain item, publish `signed-out` with reason `expired`, switch the tray icon to the attention variant. Nothing switches the icon yet; see Menu bar and window. Playback continues until the access token expires, then the Player disconnects. Signing in again restores the Resume Point, paused.

There is no sign-out. To switch accounts, delete the Keychain item.

Premium is not checked up front. Development Mode removed `product` from `GET /me`, so the only signal is the SDK's `account_error` event, which fires for non-Premium accounts. On that event the token store publishes `signed-out` with reason `not-premium` and leaves the refresh token in place.

## The Player

`player.html` loads `https://sdk.scdn.co/spotify-player.js`. Once it has loaded and the Listener is signed in, `AppModel` calls `slopify.start(volume)` with the saved volume, which creates one `Spotify.Player` named `slopify` and connects it. `getOAuthToken` posts a `token` message, and Rust answers with a fresh access token. The same step fetches the Source list.

The SDK picks FairPlay (`com.apple.fps.1_0`) through WebKit's prefixed `WebKitMediaKeys`, not standard EME. It fetches Spotify's FairPlay certificate, then posts to `api.spotify.com/v1/fairplay-license/v1/audio/license`. The app plays no part in this and sets no flag for it ([spike](https://github.com/jnsdls/slopify/issues/22)).

Events, and what each does:

- `ready`: keep the device id. On the first `ready` after launch, run the launch sequence below.
- `not-ready`: forget the device id. Show "Reconnecting" in the progress area. If no `ready` follows within 30 s, call `connect()` again, and keep doing so every 30 s. Sleep and wake, and network loss, both land here.
- `state` with a state: update the Dropdown and Now Playing, and save the Resume Point. Saves are throttled to once every 5 s while playing, and immediate on pause and on track change.
- `state` with `null`: another device took over. Show "Playing on <name>" (see Dropdown states) and poll `GET /me/player` every 10 s while in that state.
- `initialization_error`, `authentication_error`: log, then fetch an access token and `connect()` again once. A second failure shows the `error` reason in the Sign-in State.
- `account_error`: report not-premium to the token store (above).
- `playback_error`: show the message in the progress area for 5 s. If it repeats three times within a minute, stop retrying and leave the message up. This is where a DRM failure lands; the Electron spike saw a 500 from the Widevine licence server surface here.
- `autoplay_failed`: logged, nothing else.

Progress display interpolates locally: keep `position` and the time of the last state event and tick every 500 ms while playing. The page never calls `getCurrentState()`.

Transport goes straight through the SDK: `togglePlay()`, `nextTrack()`, `setVolume(v)` where `v` is 0 to 1. The media commands use `resume()` and `pause()` as well. `previousTrack()` is wired to the media key only; the Dropdown has no button. Volume changes reach the SDK at once and the state file 300 ms after the last change.

Shuffle and repeat are set once per `start_source`, after the play call: `PUT /me/player/shuffle?state=false&device_id=` and `PUT /me/player/repeat?state=context&device_id=`. Shuffle off first, then repeat. Treat any 2xx as success; this account gets 200 with a body where the docs say 204. A failure on either is logged and does not fail the start. Setting shuffle before the first play matters: the spike saw the start order drift until it was set.

### Launch sequence

On the first `ready` after launch, if a Resume Point exists:

1. `setVolume(0)`.
2. `start_source` with the Resume Point's track and position.
3. When a playing `state` names the resumed track, call `pause()`. A Resume Point without a track matches any track. WKWebView drops a pause that arrives while the track is still loading, so while playing states keep coming the Player sends the pause again, at most once a second ([ticket](https://github.com/jnsdls/slopify/issues/27)). The first paused state after a pause went out restores the saved volume. The live run cost about 0.5 s of muted play.
4. If the resumed track never shows up, restore the volume after 15 s anyway.
5. If the play call fails with a 404 or 403 (a Playlist that has gone away, or a Pasted Playlist the account can no longer see), clear the Resume Point and show the empty state. With no device id, go to Reconnecting. Any other failure restores the volume and shows in the progress area for 5 s.

Muting first means the resume produces no audible blip. If no Resume Point exists, the Dropdown shows the empty state until a Source is picked. A sign-in after `expired` runs the launch sequence again once the SDK reconnects.

### Now Playing and media keys

`app/src/now_playing.rs` owns Now Playing and the media keys through MediaPlayer.framework ([ticket](https://github.com/jnsdls/slopify/issues/29)). `navigator.mediaSession` cannot do it here. The SDK plays from a cross-origin iframe, so WebKit ignores the top frame's media session, and WebKit's own entry reads "Spotify Embedded Player" with no artist.

On every `PlaybackChanged`:

- `MPNowPlayingInfoCenter` gets title, all artists joined with commas, album, duration, elapsed time, and a playback rate of 1 or 0. The app downloads the largest album image itself, with a 15 s timeout and a 5 MB cap, and adds it as artwork when it lands.
- `playbackState` is playing when the SDK is connected and not paused, paused otherwise.
- With no track loaded, or while another device holds the session, the entry is cleared and the state set to stopped.

`MPRemoteCommandCenter` handles play, pause, stop, toggle, next and previous. Play resumes, or takes the session back while it is playing elsewhere. Stop pauses. The keyboard's media keys, AirPods and Control Center all arrive through the command center. Previous is registered even without a button so the key does not fall through to Music. No global shortcuts.

WebKit would still register its own bare entry for the SDK's media element. `player_host.rs` keeps it out through WebKit's private `RequiresPageVisibilityForVideoToBeNowPlaying` preference, set with `_setRequiresPageVisibilityForVideoToBeNowPlayingForTesting:` after a `respondsToSelector:` check. It makes a `<video>` in a hidden page ineligible for Now Playing, and the SDK plays through a `<video>` in a window that is never shown. If the selector is missing, the app logs a warning and runs with a second entry. A public WebKit setting for this would retire the SPI.

macOS lets whichever app last set `playing` own the keys. If Spotify desktop is open it mirrors the Connect session and takes Now Playing; the keys still reach playback through Spotify, only the ownership moves. v1 assumes Spotify desktop is closed and says so in the README. One physical F8 press by the owner is the acceptance test; synthetic key events cannot verify this. `media-control` from the shell does reach the command center and confirmed toggle, next and previous.

## Sources

`SourceCatalog::list` in `crates/spotify/src/sources.rs` returns Liked Songs first, then `GET /me/playlists?limit=50`, following `next` until null, mapped to `Source` with `pasted: false`. Followed playlists are included by that endpoint. `AppModel` fetches the list when the Player starts and again each time the Picker opens, and keeps showing the last list until the new one lands.

`resolve_pasted_link` accepts `https://open.spotify.com/playlist/<id>` with any query string, `spotify:playlist:<id>`, and a bare 22-character base-62 id. Anything else fails with `bad-link` before any request. It then calls `GET /playlists/<id>?fields=name,uri,images,owner.id`. A 404 fails with `not-found` (covers Spotify-owned editorial and algorithmic playlists, which Development Mode apps lost in November 2024). A 403 fails with `forbidden`. Track counts are not available for playlists the Listener does not own, so the Picker never shows one.

A Pasted Playlist is the Source only while current. It is not remembered in the Picker after another Source is picked. If the Listener wants it to stick, they follow it in Spotify and it turns up under playlists.

`start_source` in `crates/spotify/src/playback.rs` is one call per Source kind, always with `?device_id=<sdk>`:

| Source | `PUT /me/player/play` body |
| --- | --- |
| Playlist | `{ "context_uri": "spotify:playlist:<id>" }` |
| Liked Songs | `{ "context_uri": "spotify:user:<userId>:collection" }` |

With a resume argument, add `"offset": { "uri": "<trackUri>" }` and `"position_ms": <n>`. Offsets by uri were verified on both kinds ([spike](https://github.com/jnsdls/slopify/issues/14)). If the play call returns 4xx with an offset, retry once without it: the track may have left the Playlist.

The collection URI is undocumented. The spike on 2026-09-09 shows it works with offsets, against the 2021 reports that offsets were refused. If Spotify removes it, the fallback is paging `GET /me/tracks` (needs `user-library-read`) into a `uris` list of at most 100 and topping up through `POST /me/player/queue`. That path is not built in v1; the [playback research](https://github.com/jnsdls/slopify/issues/13) has the details.

`transfer_here` is `PUT /me/player` with `{ "device_ids": ["<sdk>"], "play": true }`.

## Resume Point and persisted state

One JSON file, `~/Library/Application Support/slopify/state.json`. `crates/state` owns it. The path is where Electron's `userData` put it, and the format is the Electron app's byte for byte, so an existing file carries over. Writes are debounced by 250 ms and atomic: write a temp file, then rename. Quitting flushes the pending write after the Player saves the interpolated position and any volume change still waiting.

```json
{
  "version": 1,
  "resume": { "source": { "kind": "playlist", "id": "…", "uri": "…", "name": "…", "imageUrl": "…", "pasted": false }, "trackUri": "spotify:track:…", "positionMs": 83210 },
  "volume": 0.6
}
```

Unknown `version` or an unparsable file means start fresh, not first run. Missing file means first run: register the login item (below). The Sign-in State shows because the Keychain has no refresh token.

## The Dropdown

Variant A from the [prototype](https://github.com/jnsdls/slopify/issues/9), rebuilt properly. Reference: `prototype/dropdown/index.html?variant=A` on the `prototype/dropdown` branch, screenshot at `prototype/dropdown/shots/A.png` there. The code is throwaway; the layout is the decision.

300 px wide. Height fits content, at most 560 px. Top to bottom:

1. Artwork, square, full width, corners at 4 px, from the largest image on the track's album.
2. Title, one line, ellipsised, and itself a link to the track on `open.spotify.com`, opened in the default browser with `/usr/bin/open`. Artist line under it, all artists joined with commas, the first artist linked the same way.
3. Progress bar with elapsed on the left and total on the right, `m:ss`. Display only, no seek.
4. Transport centred: one round play/pause button and a next button. No previous.
5. Volume slider, 0 to 100, no mute button.
6. "Playing from" row: the Source's thumbnail (Liked Songs uses a fixed heart tile) and name. Clicking opens the Picker in place.
7. Footer: full Spotify logo on the left (see Attribution), the Listener's display name, Quit on the right.

The Picker replaces items 1 to 5 with a list while open, keeping the footer. Order: Liked Songs, then playlists in the list's order, each with its thumbnail and name and a check on the current one, then a text field "Paste a playlist link" at the end. Picking a row starts that Source from the top and collapses the Picker. Pasting a link and pressing Enter resolves it, plays it on success, or shows the error inline under the field: "That's not a playlist link", "Spotify won't share that playlist with this app" for `not-found` and `forbidden`. Escape closes the Picker before it closes the window.

### States

- Playing or paused: the layout above. Play/pause reflects `paused`.
- Empty (signed in, no Source yet): artwork slot shows the app icon dimmed, title reads "Pick something to play", transport disabled, "Playing from" row reads "Choose a source" and opens the Picker.
- Playing elsewhere: artwork and title from `GET /me/player` if it returns an item, progress area reads "Playing on <device>". The play button is enabled and calls `transfer_here`; next and volume are disabled.
- Reconnecting: progress area reads "Reconnecting", transport disabled.
- Sign-in State: replaces everything but the footer. One line of text and a "Sign in with Spotify" button. The line depends on the reason. First run: "Sign in to start playing." Expired: "Spotify signed you out. Sign in again to keep going." Not premium: "slopify needs a Premium account." Error: the detail. While `signing-in`, the button is disabled and reads "Waiting for Spotify".

Keyboard while the window is focused: Space toggles play/pause, Right arrow is next, Escape closes the Picker or the window. Nothing global.

## Menu bar and window

- `NSStatusItem` with a monochrome template image, 22 pt, built from `resources/trayTemplate.png` and its 2x asset, both compiled into the binary. No title text. Left and right click both toggle the Dropdown.
- The attention variant with a small dot, meant only for the `expired` Sign-in State, is in `resources/` as `trayAttentionTemplate.png` but nothing loads it yet. Until something does, `expired` shows no dot.
- No Dock icon. The bundle's Info.plist sets `LSUIElement`, and `main.rs` sets the Accessory activation policy once GPUI has finished launching. GPUI sets the Regular policy at that point, which overrides `LSUIElement`, so the policy call is needed in the bundle as well as under `cargo run`.
- The Dropdown is a GPUI `PopUp` window: frameless, not movable, resizable or minimisable, created hidden at launch and never closed. `PopUp` floats over full-screen apps and joins every space. The `Transient` collection behaviour keeps it out of Mission Control. It opens centred under the status item, clamped to the nearest screen's visible frame. Its height follows its content between 120 and 560 px, with the top edge fixed.
- Showing the Dropdown activates the app, so the window stays key. It hides when it stops being key and on Escape, and hiding hands focus back to the previous app. A close request hides it. A click on the icon within 200 ms of a hide does not reopen it, so clicking the icon while the Dropdown is open closes it.
- The Player lives in its own hidden host window, so the Dropdown can come and go freely. The host window must never be shown: WebKit's Now Playing entry stays out only while the page is hidden.
- Launch at login: `login_item.rs` registers `SMAppService.mainAppService` on first run only. It needs a bundle, so a bare `cargo run` binary skips it. SMAppService needs macOS 13, which is the bundle's minimum. No toggle in the app; System Settings switches it off.

## Attribution

Checked against Spotify's design guidelines and developer policy on 2026-09-09 ([research](https://github.com/jnsdls/slopify/issues/15), full checklist with source URLs in `docs/research/spotify-attribution.md` on `research/spotify-attribution`). The Dropdown is a "playing view" in Spotify's terms, so the rules below are required, not nice to have.

- The footer shows the full Spotify logo (icon plus wordmark), at least 70 px wide, with clear space of half the icon height on every side. Use the asset from Spotify's own download, unmodified. Never the wordmark alone.
- The logo is monochrome. Spotify green is allowed only on pure black or pure white, and the Dropdown background is neither. White logo on the dark appearance, black on light. The Dropdown follows the system appearance for this reason alone; everything else may stay dark.
- The title links to the track and the artist line links to the first artist, both on `open.spotify.com`. The link beside the title from the prototype becomes the title itself being the link; no separate icon. Metadata must link to the matching entity, never to Spotify's home page.
- Artwork is shown uncropped, no overlay of any kind (no play glyph, no gradient, no text), no blur, no animation, corners rounded at 4 px. The empty state's dimmed app icon is fine because it is not Spotify content.
- Metadata is rendered exactly as the SDK returns it. A truncated title or artist line gets a tooltip with the full string.
- No playback happens without artwork and metadata on screen when the Dropdown is open. Closed Dropdown counts as a minimised view, and Now Playing carries the same metadata, so playback with the window hidden is fine. Do not add a mode that hides metadata.
- Artwork and metadata are cached only for display, in GPUI's in-memory image cache, and the Dropdown drops the previous track's artwork when the track changes. Now Playing holds one artwork image in memory. The app never touches audio. WebKit decrypts and plays it, and nothing is written to disk.
- The app icon and tray icon must not resemble the Spotify mark: no green, no circle-with-waves.
- The name "slopify" passes the letter of the naming rule (does not contain "Spotify", does not start with "Spot") but is close enough to revisit before any public release, which is out of scope anyway. The Connect device name is `slopify`.
- Spotify's policy wants a way to disconnect the app. v1 has no sign-out; the disconnect is the Listener revoking access at spotify.com/account/apps, which the app handles through the `invalid_grant` path.
- Policy asks that the app add value beyond Spotify's own client. The README says what that is: a one-click Source from the menu bar with no Spotify desktop running.

## Error handling summary

| Situation | Signal | What the Listener sees |
| --- | --- | --- |
| No refresh token | startup | Sign-in State, first-run line |
| Refresh token dead | `invalid_grant` | Sign-in State, expired line; tray dot, not wired yet |
| Network down during refresh | transport error / 5xx | nothing until the access token expires, then "Reconnecting" |
| Non-Premium account | SDK `account_error` | Sign-in State, premium line |
| Licence server refuses | SDK `playback_error` | message in the progress area; stops retrying after three in a minute |
| Another device took over | state `null` | "Playing on <device>", play transfers back |
| Playlist gone | 404/403 on play | Resume Point cleared, empty state |
| Pasted link bad or blocked | `resolve_pasted_link` fails | inline line under the paste field |
| Port 8888 busy | listen error | Sign-in State, error line |
| Spotify desktop open | Now Playing moves to Spotify | nothing in-app; README explains |

Every Web API call retries once on 429 after `Retry-After`, and once on 5xx after 1 s. A 401 refreshes the access token and retries once. Every non-2xx is logged at `warn` with method, path and status.

Logging goes through the `log` crate to `env_logger` at `info` by default; `RUST_LOG` overrides it. From a terminal the log goes to stderr. Launched from Finder or the login item it goes to `~/Library/Application Support/slopify/logs/slopify.log`, which moves to `slopify.old.log` at launch once it passes 1 MB.

## Packaging and signing

`./package.sh` runs, in order:

1. Take `SLOPIFY_SPOTIFY_CLIENT_ID` from the environment, or else from `.env.local`. Stop if neither has it.
2. `cargo build --release -p slopify` with `MACOSX_DEPLOYMENT_TARGET=13.0`.
3. Assemble `dist/slopify.app`: the binary, `build/icon.icns`, and an Info.plist with bundle id `gg.nebula.slopify`, `LSUIElement`, `LSMinimumSystemVersion` 13.0 and the crate's version. `plutil -lint` checks the plist. The tray icons, SVG icons and `player.html` are inside the binary already.
4. `codesign --force --deep --sign - dist/slopify.app`, then `codesign --verify --deep --strict`.

There is no VMP step, no EVS account and no fuse to flip. WKWebView brings its own FairPlay, so an ad-hoc signature is all the bundle needs ([ADR 0002](../adr/0002-player-in-wkwebview-ui-in-gpui.md)). CI runs `package.sh` with a placeholder client id.

Output is `dist/slopify.app`. Copy it to `/Applications` by hand. No DMG, no notarisation, no update mechanism.

## Testing and done

Unit tests run with `cargo test --workspace`. None needs a web view, Spotify or a stored Keychain item. The callback server tests bind loopback ports, and one Keychain test runs the real `security` to check the missing-item exit code.

- PKCE: verifier and challenge generation match RFC 7636 test vectors; the authorize URL carries every scope.
- Callback server: the right `state` resolves, a wrong one rejects, a busy port and the five-minute timeout reject, the server closes after the first callback.
- Keychain: the token never goes in argv, single quotes in it are escaped, a missing item reads as no token.
- Token store: refresh five minutes before expiry, rotate the refresh token when the response carries one, `invalid_grant` clears the Keychain item and publishes `expired`, network errors back off and do not sign out.
- Web API client: one refresh and retry on 401, `Retry-After` on 429, 1 s on 5xx, and a log line for every non-2xx.
- Pasted link parser: the three accepted forms with and without query strings, and rejection of track, album and artist links.
- State file: round-trips, atomic write, unknown version starts fresh, a file the Electron app wrote reads and writes back identically.
- `start_source` body builder: the two Source kinds, with and without resume, the retry without offset on 4xx, and shuffle then repeat after play.
- The Player, in `app/src/player/tests.rs`, on made-up instants: the launch sequence including the 15 s fallback, reconnecting every 30 s, the "Playing on" poll, Resume Point throttling, the volume debounce, the playback error gate and the auth retry.
- Page messages: every message type parses, and the token is quoted as a JavaScript string.
- Now Playing's mapping from Player state, the Dropdown's screen clamping, and the view rules behind every Dropdown state.

Manual checklist, done by the owner on the packaged app before v1 is called finished:

1. Fresh `~/Library/Application Support/slopify` and no Keychain item: app shows the Sign-in State, sign in completes in the browser, Dropdown lands in the empty state.
2. Pick Liked Songs: audio within 5 s.
3. Pick a followed playlist, then a pasted link to a friend's playlist, then a pasted link to a Spotify editorial playlist (expect the inline not-found line).
4. Quit mid-track, relaunch: the same track at the same position, paused, no audible blip.
5. F8, AirPods play/pause and next, and the Now Playing widget shows slopify's title and artwork. Exactly one entry, no "Spotify Embedded Player".
6. Start playback on a phone: Dropdown shows "Playing on <phone>", play in slopify takes it back.
7. Let the playlist run to the end: it loops.
8. Sleep the Mac for a minute, wake: playback resumes on play without a reconnect error.
9. `codesign --verify --deep --strict` passes on the copy in `/Applications`.

## Known unknowns

Recorded so the builder does not rediscover them:

- Whether index 0 of the Liked Songs context is the newest saved track. It does not matter for v1 because resume uses a track uri.
- The collection URI is undocumented and could vanish without a changelog entry.
- Physical media keys and AirPods have not been machine-verified. `media-control` confirmed toggle, next and previous through the command center.
- `RequiresPageVisibilityForVideoToBeNowPlaying` is WebKit SPI, and a macOS update could drop or rename it. The app checks the selector and keeps running, but Now Playing then shows a second, bare "Spotify Embedded Player" entry beside slopify's.
- Now Playing depends on the host window never being shown. The preference only counts a hidden page as ineligible, so ordering that window on screen, even for debugging, brings WebKit's entry back.
